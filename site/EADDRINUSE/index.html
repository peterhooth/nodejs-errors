Node.js Error

EADDRINUSE: address already in use

error code: EADDRINUSE

Complete reference — what it means, how to find the conflicting process, and how to fix it.

Quick Answer: Node.js throws Error: listen EADDRINUSE: address already in use :::3000 when another process is already bound to that port. On macOS/Linux, run lsof -ti:3000 | xargs kill to free it instantly. On Windows, use netstat -ano | findstr :3000 then taskkill /PID <pid> /F.

What is EADDRINUSE?

EADDRINUSE stands for Error ADDRess IN USE — a POSIX system error thrown when a server attempts to listen() on a TCP/UDP port that is already bound by another process. Only one process can own a port at a time.

Exact error message you will see:
Error: listen EADDRINUSE: address already in use :::3000
Error: listen EADDRINUSE: address already in use 0.0.0.0:8080

Full Error Example

Error: listen EADDRINUSE: address already in use :::3000
    at Server.setupListenHandle [as _listen2] (node:net:1872:16)
    at listenInCluster (node:net:1920:12)
    at Server.listen (node:net:2008:7)
    at Function.listen (/project/node_modules/express/lib/application.js:635:24)
    at Object.<anonymous> (/project/app.js:10:5) {
  code: 'EADDRINUSE',
  errno: -98,
  syscall: 'listen',
  address: '::',
  port: 3000
}

The port field in the error object tells you exactly which port is conflicted — use that number in the kill commands below.

Fix 1 – Kill the process using the port

macOS / Linux

# Find which process is using port 3000
lsof -i :3000

# Kill it in one command (replace 3000 with your port)
lsof -ti:3000 | xargs kill

# Force kill if it doesn't stop
lsof -ti:3000 | xargs kill -9

Windows (Command Prompt)

:: Find the PID using port 3000
netstat -ano | findstr :3000

:: Kill by PID (replace 12345 with the actual PID)
taskkill /PID 12345 /F

Windows (PowerShell)

# One-liner: find and kill process on port 3000
Get-Process -Id (Get-NetTCPConnection -LocalPort 3000).OwningProcess | Stop-Process -Force

Fix 2 – Change the port

If you don't control the other process (a system service, another app), use a different port. Always read the port from an environment variable so it's easy to change without touching code. 

const PORT = process.env.PORT || 3001; // fallback to 3001 if 3000 is taken

app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});

Fix 3 – Handle the error and retry automatically

For development tools or CLIs that need to find a free port automatically: 

function startServer(port) {
  const server = app.listen(port)
    .on('error', (err) => {
      if (err.code === 'EADDRINUSE') {
        console.log(`Port ${port} in use, trying ${port + 1}...`);
        startServer(port + 1);
      } else {
        throw err;
      }
    })
    .on('listening', () => {
      console.log(`Server started on port ${port}`);
    });
}
startServer(3000);

Prevention – Graceful shutdown

The most common cause of EADDRINUSE in development is a previous Node.js process that crashed or was force-quit without releasing the port. A proper shutdown handler prevents this by closing the server cleanly before the process exits. 

const server = app.listen(3000);

function shutdown() {
  server.close(() => {
    console.log('Server closed');
    process.exit(0);
  });
}

process.on('SIGTERM', shutdown); // Docker stop, Kubernetes
process.on('SIGINT',  shutdown); // Ctrl+C in terminal

Common causes

SituationSolution
Previous dev server crashed without releasing portKill with lsof -ti:PORT | xargs kill
Two terminals running the same projectClose one, or use different ports per terminal
Another app (nginx, Apache, Postgres) using the portChange your app's port
nodemon restarting before old process fully exitsAdd --delay 1000 to nodemon or add graceful shutdown
Docker container port already bound on hostChange the host port mapping in docker run -p HOST:CONTAINER

Debugging Checklist

  1. Read err.port from the error object to confirm which port is conflicted.
  2. Run lsof -i :PORT (macOS/Linux) or netstat -ano | findstr :PORT (Windows) to identify the process.
  3. Check if you have multiple terminal tabs running the same project.
  4. Check if a system service (web server, database) uses that port by default.
  5. Add a graceful shutdown handler to prevent leaving orphaned processes.
Common mistake: Using kill -9 (or taskkill /F on Windows) as the first resort skips the graceful shutdown signal. Always try kill (SIGTERM) first — it allows the process to close connections cleanly.
