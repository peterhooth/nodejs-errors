Node.js Error

UnhandledPromiseRejection

event: unhandledRejection  ·  fatal since Node.js 15

Complete reference — what it means, the Node.js 15 breaking change, all common causes, and step-by-step fixes with code examples.

Quick Answer: A Promise was rejected and nothing caught the rejection — no .catch(), no try/catch around an await. Since Node.js 15 this crashes the process with exit code 1. Fix it by adding try/catch to every async function and .catch() to every promise chain. Never call an async function without await unless you immediately chain .catch().

What is UnhandledPromiseRejection?

When a Promise is rejected and no handler is registered to catch that rejection, Node.js emits the unhandledRejection process event. The rejection is "unhandled" because no .catch() callback, no try/catch block around an await, and no Promise.allSettled() / Promise.any() absorb the error.

This is one of the most common async bugs in Node.js: code looks like it runs correctly but silently swallows errors — until Node.js 15 made the behavior fatal.

Exact error messages you will see:
UnhandledPromiseRejectionWarning: Error: something failed  (Node.js < 15)
node:internal/process/promises:279 - UnhandledPromiseRejection  (Node.js 15+)
[UnhandledPromiseRejection: This error originated either by throwing inside of an async function without a catch block, or by rejecting a promise which was not handled with .catch()]
Process exit code 1 in Node.js 15+

The Node.js 15 Breaking Change

This is the single most important fact about this error:

Node.js versionBehavior on unhandled rejection
Node.js < 15 Prints UnhandledPromiseRejectionWarning to stderr. Process continues running. (Deprecated since Node.js 12.)
Node.js 15+ (LTS 16, 18, 20, 22) Throws the rejection as an uncaught exception. Process crashes immediately with exit code 1. Same as an unhandled synchronous throw.

If you upgraded from Node.js 14 to 16+ and your process suddenly crashes with UnhandledPromiseRejection, this behavioral change is why. Bugs that were previously silently swallowed are now fatal.

Do not downgrade to Node.js 14 to "fix" this: The crash in Node.js 15+ is exposing a real bug that existed before. The warning in older versions was the bug — the process was silently ignoring errors and potentially running in a corrupt state. Fix the actual missing error handler.

Common Causes

CauseWhy it triggers the error
Async function called without await and without .catch() The returned Promise is discarded. If it rejects, no handler exists. Classic "fire and forget" bug.
Promise chain missing a .catch() handler A rejection in any .then() step propagates to the end of the chain. If the chain has no .catch(), the rejection is unhandled.
async event handler throwing without being caught EventEmitter does not await listeners. An async listener that throws returns a rejected Promise that is never observed by the emitter.
setTimeout / setInterval with an async callback that throws Timer callbacks are called synchronously by the event loop — the returned Promise from an async callback is silently discarded.
Forgetting to return a Promise inside middleware chains Express / Fastify / other frameworks expect middleware to either call next(err) or return a resolved Promise. An unreturned rejection escapes the framework's error handler.
Fire-and-forget pattern without error handling Intentionally not awaiting a background task but also not adding .catch() means any failure is silently unhandled.

Fix 1 – Add try/catch to async functions

The most direct fix: every async function that can throw must have a try/catch block, or its caller must handle the rejection. 

// BROKEN – rejection escapes
async function loadUser(id) {
  const user = await db.findUser(id); // can reject
  return user;
}

loadUser(42); // no await, no .catch() — UNHANDLED REJECTION if db.findUser rejects

// FIXED – option A: await the call and catch at call site
async function main() {
  try {
    const user = await loadUser(42);
    console.log(user);
  } catch (err) {
    console.error('Failed to load user:', err);
  }
}

// FIXED – option B: add .catch() when not awaiting
loadUser(42).catch((err) => console.error('Failed to load user:', err));

Fix 2 – Add .catch() to promise chains

Every promise chain must terminate with a .catch(). A rejection in any .then() step skips all subsequent .then() calls and lands in the nearest .catch(). 

// BROKEN – no .catch()
fetch('https://api.example.com/data')
  .then((res) => res.json())
  .then((data) => process(data));
// If fetch() or res.json() or process() rejects — UNHANDLED REJECTION

// FIXED – .catch() at the end of the chain
fetch('https://api.example.com/data')
  .then((res) => res.json())
  .then((data) => process(data))
  .catch((err) => {
    console.error('API request failed:', err);
  });

// FIXED – equivalent with async/await
async function loadData() {
  try {
    const res = await fetch('https://api.example.com/data');
    const data = await res.json();
    process(data);
  } catch (err) {
    console.error('API request failed:', err);
  }
}

Fix 3 – Handle rejections in async event listeners

EventEmitter is not Promise-aware. An async listener that throws does not propagate the error to the emitter's 'error' event. Wrap the listener body in try/catch. 

const EventEmitter = require('events');
const emitter = new EventEmitter();

// BROKEN – async listener, rejection is not caught by the emitter
emitter.on('data', async (payload) => {
  const result = await processPayload(payload); // can reject
  await saveResult(result);                      // can reject
});

emitter.on('error', (err) => console.error('emitter error:', err));
// This 'error' listener does NOT catch async listener rejections!

// FIXED – wrap async listener in try/catch
emitter.on('data', async (payload) => {
  try {
    const result = await processPayload(payload);
    await saveResult(result);
  } catch (err) {
    // Handle the error here — or emit it to the error handler:
    emitter.emit('error', err);
  }
});

Fix 4 – Handle async callbacks in setTimeout / setInterval

Timer callbacks are invoked synchronously by the event loop. The Promise returned by an async timer callback is discarded. Any rejection is unhandled. 

// BROKEN – async callback, rejection escapes
setTimeout(async () => {
  await doSomethingThatMightFail(); // UNHANDLED REJECTION if this rejects
}, 1000);

// FIXED – wrap in try/catch
setTimeout(async () => {
  try {
    await doSomethingThatMightFail();
  } catch (err) {
    console.error('Timer callback error:', err);
  }
}, 1000);

// ALTERNATIVE – extract to a named async function with its own error handling
async function timerTask() {
  try {
    await doSomethingThatMightFail();
  } catch (err) {
    console.error('Timer task error:', err);
  }
}

setInterval(timerTask, 5000);

Fix 5 – Use process.on('unhandledRejection') as a last resort

A global handler is useful for centralized logging and graceful shutdown, but it is not a substitute for proper per-Promise error handling. Every rejection that reaches this handler represents a bug. 

// Last-resort handler — log and exit gracefully
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled Promise rejection at:', promise, 'reason:', reason);
  // In production: report to error tracking (Sentry, Datadog, etc.)
  // Always exit — running with an unhandled rejection means unknown state
  process.exit(1);
});

// DO NOT do this — silently swallowing hides real bugs:
process.on('unhandledRejection', () => {}); // WRONG

// DO NOT do this — catching without exiting leaves process in unknown state:
process.on('unhandledRejection', (reason) => {
  console.error(reason); // logs but does not exit — WRONG in Node.js 15+
});
Node.js 15+ ignores return values from the unhandledRejection handler: In Node.js 15+, even if you register a process.on('unhandledRejection') handler, the default behavior is throw — the process will still crash unless you explicitly call process.exit() or use --unhandled-rejections=warn (not recommended for production).

Fix 6 – Enable no-floating-promises lint rule

The TypeScript ESLint rule @typescript-eslint/no-floating-promises flags any Promise-returning call that is not awaited and has no .catch(). Catching this at lint time prevents runtime crashes. 

// Install:
// npm install --save-dev @typescript-eslint/eslint-plugin @typescript-eslint/parser

// .eslintrc.json (or eslint.config.js):
{
  "parser": "@typescript-eslint/parser",
  "plugins": ["@typescript-eslint"],
  "rules": {
    "@typescript-eslint/no-floating-promises": "error",
    "@typescript-eslint/no-misused-promises": "error"
  }
}

// The rule catches:
someAsyncFunction();           // ERROR: floating promise
arr.forEach(async (item) => { // ERROR: no-misused-promises
  await processItem(item);
});

// Correct:
await someAsyncFunction();
someAsyncFunction().catch(handleError);
await Promise.all(arr.map(async (item) => processItem(item)));

Fix 7 – Fix the async forEach anti-pattern

Using Array.prototype.forEach with an async callback is one of the most common sources of unhandled rejections. forEach ignores the returned Promise. Use Promise.all with .map() instead. 

const items = [1, 2, 3];

// BROKEN – forEach discards the Promise returned by each async callback
items.forEach(async (item) => {
  await processItem(item); // UNHANDLED REJECTION if processItem rejects
});

// FIXED – Promise.all + map: all rejections are captured
await Promise.all(items.map(async (item) => {
  await processItem(item);
}));

// FIXED – for...of loop (sequential, easier to read):
for (const item of items) {
  try {
    await processItem(item);
  } catch (err) {
    console.error('Failed on item', item, err);
  }
}

// FIXED – with individual error handling per item (parallel, independent):
await Promise.allSettled(items.map(async (item) => {
  try {
    await processItem(item);
  } catch (err) {
    console.error('Failed on item', item, err);
  }
}));

Fix 8 – Handle async errors in Express middleware

Express 4 does not catch Promise rejections from async route handlers. Either wrap handlers with a helper, or upgrade to Express 5 which handles this natively. 

// BROKEN in Express 4 – async handler, rejection is not forwarded to Express error handler
app.get('/user/:id', async (req, res) => {
  const user = await db.findUser(req.params.id); // rejects = UNHANDLED REJECTION
  res.json(user);
});

// FIX A – wrap with asyncHandler helper (Express 4)
const asyncHandler = (fn) => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

app.get('/user/:id', asyncHandler(async (req, res) => {
  const user = await db.findUser(req.params.id);
  res.json(user);
}));

// FIX B – express-async-errors package (Express 4)
// npm install express-async-errors
require('express-async-errors'); // patch Express to handle async errors
app.get('/user/:id', async (req, res) => {
  const user = await db.findUser(req.params.id);
  res.json(user);
});

// FIX C – Express 5 (handles async natively)
// npm install express@5
app.get('/user/:id', async (req, res) => {
  const user = await db.findUser(req.params.id); // rejections auto-forwarded to next(err)
  res.json(user);
});

// In all cases, register an Express error handler:
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: err.message });
});

Debugging: Finding the Source

When the error message does not include a useful stack trace, use these techniques to locate the exact promise that is rejecting.

Read the stack trace carefully

The stack trace in the unhandledRejection event points to where the rejected Promise was created, not where it was called. Look for your own source files in the trace — ignore node:internal/ frames. 

# Force throw behavior even on older Node.js versions
node --unhandled-rejections=throw app.js

# See all async hooks activity (verbose, for deep debugging)
NODE_DEBUG=promise node app.js

Use --trace-warnings for deprecation context

# Shows the full stack trace for DeprecationWarnings including promise warnings
node --trace-warnings app.js

Identify the rejection reason and promise

process.on('unhandledRejection', (reason, promise) => {
  console.error('=== UNHANDLED REJECTION ===');
  console.error('Promise:', promise);
  console.error('Reason:', reason);
  if (reason instanceof Error) {
    console.error('Stack:', reason.stack);
  }
  process.exit(1);
});

Use AsyncLocalStorage to track context

const { AsyncLocalStorage } = require('async_hooks');
const requestContext = new AsyncLocalStorage();

// Wrap each request in a context store so you know which request
// triggered the unhandled rejection:
app.use((req, res, next) => {
  requestContext.run({ requestId: req.id, url: req.url }, next);
});

process.on('unhandledRejection', (reason) => {
  const ctx = requestContext.getStore();
  console.error('Unhandled rejection in request context:', ctx, reason);
  process.exit(1);
});

Debugging Checklist

  1. Search your codebase for async functions called without await — any of them can produce an unhandled rejection.
  2. Search for .then( without a matching .catch( at the end of the same chain.
  3. Search for forEach(async — replace all with Promise.all(arr.map(async.
  4. Check Express route handlers — they need either a wrapper or Express 5 to safely use async.
  5. Check EventEmitter listeners — any async listener needs its own try/catch.
  6. Check setTimeout / setInterval callbacks — wrap async timer callbacks in try/catch.
  7. Add the @typescript-eslint/no-floating-promises and @typescript-eslint/no-misused-promises rules to catch these statically.

Related Errors

  • TypeError: Cannot read properties of undefined — often the underlying rejection reason inside an async function
  • ERR_UNHANDLED_REJECTION — the error code property set on the thrown rejection object in Node.js 15+
  • UnhandledPromiseRejectionWarning — the older form of this error emitted as a process warning in Node.js < 15
  • PromiseRejectionHandledWarning — emitted when a .catch() is attached to a Promise after the current tick (too late to prevent the unhandledRejection event)
  • uncaughtException — the synchronous equivalent: a thrown error with no surrounding try/catch
