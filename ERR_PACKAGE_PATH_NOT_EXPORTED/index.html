Node.js Error

ERR_PACKAGE_PATH_NOT_EXPORTED

Complete reference: what it means, why it happens, and how to fix it.

What is ERR_PACKAGE_PATH_NOT_EXPORTED?

ERR_PACKAGE_PATH_NOT_EXPORTED is a Node.js runtime error thrown when your code attempts to import or require() a file path inside an npm package that the package intentionally does not expose. Node.js enforces the exports map in package.json strictly: any subpath not listed there is treated as private and inaccessible, even if the file physically exists on disk.

Error message you will see:
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/internal/foo' is not defined by "exports" in …/node_modules/some-package/package.json

Root Cause

The error originates from Node.js's package exports map feature, introduced in Node.js 12 and enforced strictly from Node.js 12+. When a package.json contains an "exports" field, Node.js uses it as the sole source of truth for which paths are importable. Deep imports that previously worked (before the package added an exports map) suddenly fail.

Example: package that triggers the error

// node_modules/some-package/package.json
{
  "name": "some-package",
  "exports": {
    ".": "./dist/index.js"
  }
}

// your code – this BREAKS
import { helper } from 'some-package/lib/utils';
// → ERR_PACKAGE_PATH_NOT_EXPORTED

Only the root export (".") is defined. The subpath ./lib/utils is not in the exports map, so Node.js refuses to load it.

Common Triggers

  • Upgrading a package that added an exports field in a minor/patch version
  • Importing internal paths like package/lib/…, package/src/…, or package/dist/…
  • Using ESM import statements for paths that were only reachable via CommonJS require
  • Mixing ESM and CJS in a monorepo with strict package boundaries
  • Packages that intentionally removed deep-import support as a breaking change

How to Fix ERR_PACKAGE_PATH_NOT_EXPORTED

Fix 1 – Use only the package's public API

Check the package's README or changelog for the intended public import path.

// Before (broken)
import { helper } from 'some-package/lib/utils';

// After (correct)
import { helper } from 'some-package';
// or the documented subpath, e.g.:
import { helper } from 'some-package/utils';

Fix 2 – Add the missing export (if you own the package)

// package.json – add the subpath you need to expose
{
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js",
    "./lib/*": "./dist/lib/*.js"
  }
}

Fix 3 – Pin to an older version

If the package added the exports map in a recent release and broke your import, pin to the last version that did not have it while you migrate: 

npm install some-package@2.3.0

Fix 4 – Patch with patch-package

If you cannot change your import path and cannot upgrade, use patch-package to temporarily add the missing export to the dependency's package.json: 

npx patch-package some-package

Fix 5 – Alias via bundler (webpack / Vite / esbuild)

Map the private path to a public one inside your bundler config instead of importing it directly.

// vite.config.ts
resolve: {
  alias: {
    'some-package/lib/utils': 'some-package/utils'
  }
}

Condition / Conditional Exports

Modern packages use conditional exports to serve different files to ESM and CJS consumers. A misconfigured conditions map is another source of this error: 

{
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js",
      "default": "./dist/index.js"
    }
  }
}

If your environment doesn't match any condition and no "default" is set, Node.js throws ERR_PACKAGE_PATH_NOT_EXPORTED.

Affected Node.js Versions

Node.js versionBehaviour
< 12.7exports field ignored; deep imports always work
12.7 – 12.16exports honoured but with warnings
12.17+ / 14+exports strictly enforced; error thrown on violation
16, 18, 20, 22 (LTS)Strict enforcement; no opt-out

Debugging Checklist

  1. Read the error message – it tells you the exact subpath that is missing.
  2. Open node_modules/<package>/package.json and inspect the exports field.
  3. Check the package's GitHub releases/changelog for migration notes.
  4. Search for the package name + ERR_PACKAGE_PATH_NOT_EXPORTED in the package's issue tracker.
  5. Run node --version – confirm you are on a version that enforces exports.
Common mistake: Adding "./lib/*": "./lib/*" wildcard exports fixes the error locally but exposes all internal files publicly. Only export paths you intend to be part of your public API.
